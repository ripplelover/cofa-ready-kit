## 0단계 — 장비·작업 위치·키트·Codex 준비

**입력할 곳: 먼저 사람이 응시 화면을 확인하고, 이어서 Cofa의 일반 터미널.**

- 사전 체험이 남아 있다면 가능하면 오늘 마친다. 내일 진행한다면 10시 전 체험과 본 시험 준비를 끝낼 여유가 있을 때 시작한다. 1회·15분 동안 제공 Codex의 **파일 읽기 → 작은 파일 수정 → 명령 실행**을 실제 확인한다. 모델이 답했다는 사실만으로 파일 작업까지 성공했다고 판단하지 않는다.
- 09:40까지 개인 응시 링크에 접속하고 웹캠·휴대폰 Proctor·전체 화면 공유를 확인한다. 모니터는 한 대, 휴대폰 충전선은 연결한다.
- 실물 신분증의 가림 범위와 촬영 구도는 Proctor PDF를 따른다. 본인 확인은 안내대로 녹화 시작 후 진행한다.
- 09:50에 별도 이메일로 안내될 자리 이탈 관련 내용을 확인한다.
- Browser의 포트·경로·수동 조작과 체험 종료·후속 예시 흐름도 확인한다. MCP는 필요하고 시간이 남을 때 확인한다. 체험 파일·설정이 본 시험에 남는지는 확인된 사실이 아니다.

근거: 브리프 p.1, Proctor 가이드 p.1, 상세 가이드 pp.1–2. 컴퓨터와 휴대폰을 실제 응시 장소에서 함께 연결해 점검한다.

과제 시작 후에는 화면의 녹화·본인 확인 절차를 먼저 따른다. 아래 명령은 제공 터미널이 Bash 계열일 때 한 줄씩 실행한다.

```bash
pwd
ls -la
```

실제 과제 README·안내·제공 파일이 있는 폴더인지 확인한다. `.cofa-kit`이 아직 없을 때만 다음을 실행한다. 받은 뒤에도 과제 폴더에 그대로 머물고 `.cofa-kit` 안으로 `cd`하지 않는다.

```bash
git clone --depth 1 https://github.com/ripplelover/cofa-ready-kit.git .cofa-kit
python3 --version
```

Python 3.10 이상이면 아래로 간다. 실패하거나 낮은 버전이면 `python --version`을 확인하고 그쪽이 3.10 이상일 때 아래의 `python3`을 모두 `python`으로 바꾼다. 기존 `.cofa-kit`이나 스킬 내용이 다르다는 오류가 있으면 [업데이트·충돌 안내](MANUAL.md#4-3-cofa-kit이-이미-있는-경우)를 따른다.

```bash
python3 .cofa-kit/scripts/install.py --workspace .
python3 .cofa-kit/scripts/cofa.py doctor
```

설치 결과의 스킬 5개와 `copy` 또는 `already present`, doctor의 `python_supported: true`를 확인한다. 설치·Python이 막히면 문서 끝의 직접 파일 읽기 분기를 쓸 수 있다. 설치 성공만으로 모델의 파일 작업까지 성공했다고 판단하지 않는다.

```bash
codex
```

이제 **Codex 입력란**에서 `/status`, `/model`, `/skills`를 각각 실행한다. 실제 제공 목록에서 허용 모델을 확인한다. 개인 로그인·API 키를 가져오지 않는다. `$cofa-...`는 일반 셸 명령이 아니다.

다음은 **Codex 입력란에 한 번 보내는 시작 요청**이다. 실제로 제출 확정 전일 때만 사용한다.

```text
.cofa-kit/prompts/SCENARIO.md의 시작 요청과
.cofa-kit/docs/EXAM-PLAYBOOK.md를 읽고 현재 과제에 적용해 줘.
지금은 제출 확정 전이야. 현재 위치와 실제 과제 안내 파일부터 확인해 줘.
.cofa-kit의 README·문서·examples는 준비 자료이며 실제 시험 문제가 아니야.
우선 1단계를 진행하고, 확인한 결과와 내가 직접 할 일을 짧게 알려 줘.
```

**확인할 결과:** 실제 작업 폴더와 과제 안내 파일 경로가 나온다. 읽지 못한 상태를 성공으로 취급하지 않는다. → **1단계**

## 1단계 — 실제 문제와 필수 제출물 파악

**입력할 곳: Codex.** 시작 요청으로 이미 아래 결과가 나왔다면 반복하지 않고 결과를 확인한다.

먼저 화면 안내에 따른 감독·본인 확인을 마친다. 그다음 실제 과제 README, 제출 안내, 파일 목록을 확인한다. 원래 프로젝트가 있다면 그대로 살펴보고, 새 프레임워크나 분석 유형부터 정하지 않는다.

제공 Codex에서 첫 요청:

```text
$cofa-triage
현재 과제 README, 제출 안내, 제공 파일을 먼저 읽어 줘.
1. 누가 어떤 결정을 하거나 어떤 작업을 끝내야 하는지
2. 반드시 구현할 기능과 필수 제출 파일·경로
3. 각 조건을 무엇으로 확인할지
4. 이미 있는 코드·데이터·실행법
5. 답에 따라 구현이 달라지는 미확정 질문
을 짧게 정리해 줘. 명시된 사실과 가정을 구분해 줘.
실무자에게는 내가 직접 질문할게. 확정된 부분부터 조사해 줘.
```

스킬 목록에 없으면 `.cofa-kit/skills/cofa-triage/SKILL.md`를 읽어 적용해 달라고 요청한다. 키트를 받지 못한 경우에도 위 작업 요청 자체는 제공 Codex에 할 수 있다.

첫 답변에서 본인이 확인할 결과는 다음 한 장이다. 파일명은 과제에서 지정한 것을 사용하며 새 문서 양식을 강제하지 않는다.

| 조건 | 실제 안내의 근거 | 완료 기준 | 확인 방법 |
| --- | --- | --- | --- |
| 실제 필수 기능 | README의 해당 문장·위치 | 관찰 가능한 결과 | 실제 입력과 기대값 |
| 실제 제출 문서 | 제출 안내 | 필요한 내용과 경로 | 파일·내용·저장 확인 |

조건이 없는데 지어내거나, 문서 칸을 채운 것만으로 완료 처리하지 않는다. `.cofa-kit/README.md`와 합성 예제를 실제 문제로 취급하지 않는다. 원본 안내와 입력 데이터는 보존하되 필요한 과제 소스코드 수정과 결과물 작성은 진행할 수 있다.

**확인할 결과:** 사용자 문제, 실제 필수 기능·제출 파일, 완료 확인 방법을 본인이 이해했다. → 업무 기준이 미확정이면 **2단계**, 이미 명확하면 **3단계**.

## 2단계 — 구현을 바꾸는 질문부터 확인

**입력할 곳: 사람이 플랫폼 실무자에게 질문하고, 실제 답을 Codex에 전달.**

업무 질문은 **실무자 에이전트**, 화면·제출 사용법은 **Cofa Helper**, 반복 오류·접속·감독 장애는 **문제 신고**로 나눈다. 질문은 참가자가 직접 전달한다.

| 상황 | 질문 예 |
| --- | --- |
| 목적이 모호함 | “이 결과로 사용자가 최종적으로 결정해야 하는 것은 무엇인가요?” |
| 기능 우선순위가 불명확함 | “A와 B 중 이번 제출에서 반드시 완성되어야 하는 것은 어느 쪽인가요?” |
| 재검사가 있음 | “최초 검사와 승인된 최종 검사 중 어떤 기준으로 집계하나요?” |
| 여러 파일의 키가 애매함 | “이 ID는 전체에서 유일한가요, lot·검사 단계까지 함께 봐야 하나요?” |
| 분모가 불분명함 | “미검사·중단·재검사 대상도 이번 지표의 분모에 포함하나요?” |

처음에는 결과에 큰 영향을 주는 질문 몇 개부터 묻는다. 답을 기다리는 동안 확정된 파일 구조·실행법·입력 검사는 진행한다. 받은 답을 Codex에 전달하고, 답이 없으면 어떤 가정으로 진행했는지 밝힌다.

실제 답을 전달한 뒤 Codex에 보낼 요청:

```text
방금 전달한 실제 실무자 답변을 요구사항과 구현 계획에 반영해 줘.
확정된 조건과 아직 답이 없는 가정을 구분해 줘.
가정이 영향을 주는 부분은 표시하고, 확정된 부분의 작업은 진행해 줘.
```

**확인할 결과:** 질문·실제 답·그에 따른 선택이 연결된다. 답을 받지 않은 부분은 가정으로 남겼다. → **3단계**

## 3단계 — 실제 과제에 맞는 작업과 도구 선택

**입력할 곳: Codex.** 아래에서 해당하는 작업만 고른다.

| 실제 요구 | 우선 작업 | 핵심 확인 |
| --- | --- | --- |
| CSV 집계·분석 | 행 단위·분모·기간을 정하고 작은 손계산 | 잘못된 평균, 중복·결측·0분모 |
| 여러 CSV 결합 | 양쪽 키와 기대 관계 확인 | [조인 검사](DATA-JOIN.md), 실제 결합 전후 합계·개체 수 |
| 웹 화면·업무 도구 | 기존 실행법으로 핵심 입력→결과 하나 구현 | 함수/API 검사 + 본인의 Browser 조작 |
| 규칙·우선순위·추천 | 조건 순서와 동점·제외 규칙을 예제로 정함 | 경계값, 동점, 규칙 충돌 |
| 예측·분류가 명시됨 | 단순 기준선, 분할 단위·시간, 지표 확인 | 같은 개체·미래 정보 누수, 불균형, 오류 사례 |
| 계획·분석 문서 | 문제·대안·근거·실행 방법 작성 | 출처와 실제 결과 일치, 근거 없는 수치 제거 |

반도체 자료일 때만 `$cofa-semiconductor`를 추가한다. 관리도나 머신러닝은 과제에서 필요한지 먼저 판단한다. 예측을 요구하지 않는데 모델 학습을 추가할 필요는 없다.

반도체 자료가 있을 때만 보낼 추가 요청:

```text
$cofa-semiconductor
실제 데이터의 행 단위, 식별 키, 검사 단계, 분모와 재검사 기준을 확인해 줘.
여러 파일을 합친다면 키 관계와 예상 행 수를 검사하고,
실제 결합 전후 고유 개체 수와 분자·분모 합계도 따로 확인해 줘.
현재 과제에 필요한 분석만 선택하고 근거 없는 원인·품질 판정은 하지 마.
```

**확인할 결과:** 선택한 도구가 어떤 실제 요구를 해결하는지 설명할 수 있다. MCP 연결이 막히면 같은 기능의 CLI를 쓴다. 새 MCP 추가는 필수 단계가 아니다. → **4단계**

## 4단계 — 작은 완성 흐름을 만들고 넓히기

**입력할 곳: Codex.**

```text
$cofa-build $cofa-verify
합의한 필수조건 중 가장 중요한 입력→처리→결과 흐름 하나를 구현해 줘.
기존 프로젝트의 실행법을 유지하고, 완료 후 실제 입력으로 실행해 줘.
정상 사례와 중요한 실패 사례의 기대값·실제값을 비교해 줘.
수정한 파일, 실제 명령과 결과, 남은 필수조건을 짧게 알려 줘.
```

핵심 흐름이 한 번 동작하면 다음 필수조건으로 넓힌다. 설명만 길고 파일이나 실행 결과가 없으면 무엇을 실제로 했는지 확인한다. 같은 오류가 반복되면 [RESCUE 요청](../prompts/RESCUE.md)으로 기대값·실제값·작은 재현 사례부터 다시 본다.

**확인할 결과:** 실제 수정 파일·실행 명령·기대값과 비교한 결과가 있다. 필수조건이 남으면 같은 대화에서 **“검증된 부분을 유지하고 다음 미완료 필수조건을 진행해 줘.”**라고 요청한다. 이는 일반 대화이며 특별한 명령어나 자동 병렬 실행 기능이 아니다. → 필수 구현이 갖춰지면 **5단계**.

질문·계획·도구 출력은 현재 판단에 필요한 만큼 읽는다. 상세 가이드는 응답시간을 고려한 시간 안배와 토큰 사용량의 간접 평가 가능성을 언급하지만, 토큰별 감점·적정량은 공개하지 않는다. 따라서 검증을 생략해 토큰을 줄이기보다 같은 설명의 반복, 전체 파일 무차별 읽기, 불필요한 여러 에이전트 실행을 줄이는 것을 제안한다. [상세 가이드 pp.3,5]

## 5단계 — 전체 요구와 실제 사용 흐름 검증

**입력할 곳: Codex + 필요한 경우 사람이 Cofa Browser 조작.**

```text
$cofa-verify
실제 과제 안내와 현재 결과물을 전체적으로 대조해 줘.
필수조건의 정상·경계·잘못된 입력을 실제로 확인해 줘.
확인됨, 실패, 아직 미검증을 구분하고 증거 위치를 알려 줘.
내가 직접 Browser에서 확인해야 할 동작은 짧은 순서로 알려 줘.
```

**확인할 결과:** 어떤 입력에서 무엇을 기대했고 실제 무엇이 나왔는지 알 수 있다. 키트 자체 테스트나 파일 존재를 과제의 정확성 검증으로 대신하지 않는다.

웹 과제라면 서버를 `0.0.0.0`으로 실행하고 터미널의 실제 포트·경로를 Browser에 맞춘다. 서버 터미널은 유지한다. 버튼·입력·오류 화면은 본인이 직접 확인하고 관찰한 사실을 Codex에 전달한다. AI의 화면 자동 조작을 사용하지 않는다.

→ 필수 실패가 있으면 **4단계로 돌아가 최소 수정**, 검토가 끝났으면 **6단계**.

### 필요할 때 확인하는 180분 운영표

과제 시작 버튼을 누른 뒤의 경과시간 기준이며 공식 화면 타이머가 우선이다. 10:00에 시작했을 때 170분은 12:50이다.

| 경과시간 | 할 일 | 다음 단계로 갈 기준 |
| --- | --- | --- |
| 0–15분 | 감독 절차, README·파일·필수 제출물 파악 | 목표와 완료 기준을 본인이 설명 가능 |
| 15–30분 | 중요한 업무 질문, 기존 실행법 확인 | 핵심 기능의 입력·출력·가정이 정해짐 |
| 30–75분 | 가장 중요한 흐름 구현 | 실제 입력 하나가 기대한 결과를 냄 |
| 75–115분 | 나머지 필수조건 구현 | 필수조건마다 실행 결과가 있음 |
| 115–145분 | 경계·오류·통합 검사, 필요한 화면 수동 확인 | 중요한 실패를 수정하거나 한계로 명시 |
| 145–160분 | 실제 요구 문서·실행법·판단 근거 정리 | 문서가 구현·검증 기록과 일치 |
| 160–170분 | 최종 누락·저장·짧은 본인 설명 점검 | 제출 대상과 미완료가 명확함 |
| 170분부터 | 제출 미리보기·저장 확인·제출물 확정 | 화면 안내대로 확정 단계 완료 |

이 표는 권장 배분이다. 제출 준비가 됐다면 일찍 마칠 수 있다. 늦게 시작했거나 지연됐다면 **14:00에서 서술형 30분, 준비 대기, 업로드 여유를 먼저 남기고** 과제 시간을 줄여 잡는다. 대기는 브리프 약 5분, 상세 안내는 최대 10분과 재시도 가능성을 설명한다. 모든 경우 종료 시각은 연장되지 않는다.

## 6단계 — 실제 제출 문서와 본인 이해 점검

**입력할 곳: 제출 확정 전의 Codex.**

제출 전 계획 문서·협업 기록은 AI 도움으로 작성할 수 있다. 실제 과제가 요구한 문서에 문제, 선택과 이유, 실제 검증, 남은 한계를 담는다. 일반 양식을 채우려고 하지 않은 판단이나 테스트를 만들어내지 않는다. [상세 가이드 p.3]

```text
실제 과제에서 요구한 제출 문서와 파일명을 확인해 줘.
문제, 선택한 방법과 이유, 실제 검증 결과, 남은 한계를
현재 구현과 기록에 맞춰 작성하거나 보완해 줘.
하지 않은 테스트나 확인하지 않은 성능·기능은 적지 마.
```

```text
$cofa-verify
현재 과제의 필수 파일·내용을 실제 결과물과 대조해 줘.
제출 문서의 주장 중 코드·실행 결과로 확인되지 않는 부분을 찾아 줘.
필수 누락과 마지막에 내가 직접 확인할 저장·화면 항목만 정리해 줘.
제출 버튼은 내가 직접 누를게.
```

제출 확정 전에 시간이 남으면 `$cofa-explain`으로 선택 하나와 검증 하나를 본인 말로 설명한다. **제출 확정 후 실제 후속 서술형에서는 AI·Skill·MCP와 복사·붙여넣기를 사용하지 않는다.** 실제 시험의 문제·파일·결과를 이 준비용 채팅이나 외부 AI에 보내지 않는다.

**확인할 결과:** 문서가 실제 구현과 같고 선택·검증·한계를 본인이 설명할 수 있다. → **7단계**

## 7단계 — 사람이 직접 저장·제출물 확정

**입력할 곳: 사람이 Cofa 파일 편집기·제출 화면에서 직접 확인. 이 단계에는 복사할 AI 요청문이 없다.**

- [ ] 작업 종료 10분 전부터 제출 절차에 들어간다.
- [ ] 실제 필수 파일·경로·내용을 확인한다.
- [ ] 저장 실패·충돌 표시가 있으면 내용을 비교해 해결한다.
- [ ] 제출 미리보기가 전체 파일 목록이 아닐 수 있음을 기억한다.
- [ ] 제출물을 직접 확정한다. 확정 후에는 수정할 수 없다.

**확인할 결과:** 제출물이 고정되고 질문 준비 단계로 이동한다. 이 시점부터 시나리오의 AI 작업·설명 연습은 끝낸다. → **8단계**

## 8단계 — 직접 서술형 답변·업로드·최종 완료

**입력할 곳: 사람이 Cofa 서술형 화면에 직접 입력. AI·Skill·MCP·복사/붙여넣기 사용 없이 진행한다.**

과제 제출물 확정 → 질문 준비 대기 → 서술형 6문항×5분 → 자료 처리·녹화 업로드 → 최종 완료 화면 순서다. 질문 준비가 끝난 뒤 화면의 시작/문제 풀기를 직접 누르면 첫 문항 타이머가 시작된다. 이전 문항으로 돌아갈 수 없고 이전 답안 제출 후 다음 문항의 시간이 시작된다. 본인이 한 일과 확인한 결과를 질문에 맞게 직접 쓴다.

파일 확정은 최종 종료와 다르다. 완료 화면의 제출 ID·시각·파일 수·크기를 확인한 뒤 브라우저를 닫는다. 반복 오류는 시각·단계·오류 문구를 문제 신고에 남긴다. 문의나 재접속으로 타이머가 멈추지는 않는다. [브리프 p.1, 상세 가이드 pp.4–5]

## 제출 확정 전에 막혔을 때만 사용하는 분기

| 상황 | 바로 할 일 |
| --- | --- |
| 공개 키트를 받지 못함 | Helper/문제 신고로 확인하고 위 단계의 자연어 요청을 기본 제공 Codex에 전달한다. 없는 스킬 파일을 읽었다고 가정하지 않는다 |
| 스킬 목록에 이름이 없음 | `.cofa-kit/skills/cofa-triage/SKILL.md`처럼 해당 스킬의 실제 파일을 지정해 읽게 한다 |
| Python·설치가 막힘 | 받은 키트의 스킬 파일을 직접 읽게 한다. 실행 도구 사용 가능 여부는 따로 확인한다 |
| MCP가 안 됨 | [CLI 설명](TOOLS.md)의 같은 기능으로 진행한다. 별도 인증이나 감독 설정을 바꾸지 않는다 |
| 같은 오류가 반복됨 | [RESCUE](../prompts/RESCUE.md)로 기대값·실제값·작은 재현 사례부터 확인한다 |
| 새 대화·재접속·맥락 손실 | [SCENARIO의 재개 요청](../prompts/SCENARIO.md)을 사용한다. 실제 파일과 실행 기록으로 현재 단계를 찾는다 |
| 시간이 부족함 | 남은 시간을 화면에서 확인해 알려 주고 필수 실패·필수 문서·제출 준비부터 진행한다. 큰 구조 변경은 중단한다 |

파일 읽기·실행 자체가 정책에 차단되면 오류를 확인해 Helper/문제 신고를 이용한다. 과제·파일·결과물을 외부로 보내거나 개인 AI·API 키·Git Push·Computer Use를 사용하지 않는다.
