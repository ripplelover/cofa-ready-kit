# 사전 준비와 시험 당일 시간 배분

[시험 첫 화면](../README.md) · [전체 문서 지도](INDEX.md)

대상 일정: **2026-10-30(금) 준비 → 10-31(토) 09:40 접속, 10:00 시작, 14:00 전체 종료**. 기본 시작은 [README](../README.md)를 따른다. 이 문서는 사전 체험·시간 배분의 상세 참고이며 전부 읽고 시작할 필요는 없다. 아래 시간 배분과 연습 방법은 이 키트의 제안이다. 공식 사실은 [RULES.md](RULES.md)에 출처별로 정리했다.

실제 과제와 채점 가중치는 아직 모른다. 준비의 목표는 **시험 당일 처음 보는 요구사항을 짧은 시간 안에 확인하고 작동·검증·설명까지 마치는 절차를 익히는 것**이다.

문제를 받은 뒤 바로 따라갈 요청문과 분기표는 [당일 실행 안내](EXAM-PLAYBOOK.md)에 있다. 스킬·MCP를 더 추가할지 결정한 이유는 [조사 결과](RESEARCH.md), 새 두 CSV 관계 검사는 [조인 실습](DATA-JOIN.md)을 참고한다.

## 시험 전 준비: 먼저 환경, 그다음 한 번의 연습

지금 남은 시간에 따라 아래를 앞에서부터 수행한다. 사전 체험은 1회뿐이므로 장비와 공개 저장소 준비를 먼저 끝내고 사용한다.

| 권장 소요 | 할 일 | 끝났다는 기준 |
| --- | --- | --- |
| 15분 | PDF와 RULES 읽기. 허용 AI, 자료 반입, 제출 단계 확인 | “과제 문서는 AI 가능, 후속 서술형은 불가”를 구분할 수 있음 |
| 20분 | 실제 응시 자리·단일 모니터·웹캠·휴대폰 충전·유선 키보드 확인 | 손·얼굴·모니터가 함께 잡히고 네트워크 업·다운을 확인함 |
| 15분 | 공개 준비 저장소 게시·검토 | 로그아웃 상태에서도 README와 코드에 접근 가능. 개인 접속 정보·PDF·실제 과제 자료 없음 |
| 15분 | 아래 사전 체험 실행 | Codex 응답, 파일 저장, Browser, 질문 창, 제출 흐름을 한 번 확인함 |
| 45–60분 | 작은 가상 과제 한 번 수행 | 핵심 기능 하나와 정상·실패 검증이 실제로 돌아감 |
| 15분 | AI를 끄고 자신의 구현을 설명 | 선택 이유·실패 사례·한계를 직접 타이핑할 수 있음 |

이미 늦었다면 가상 과제는 줄여도 장비·사전 체험·제출 흐름은 우선 확인한다. 새 프레임워크를 여러 개 배우거나 MCP를 계속 추가하는 일은 실제 사용 준비가 된 뒤에 판단한다.

연습 과제는 예를 들어 “작은 CSV를 읽어 조건에 맞는 항목을 고르고, 근거와 요약을 출력하는 도구” 정도면 충분하다. 웹 화면이 필요하다고 가정해도 입력 → 처리 → 결과 확인 하나에 집중한다. **예상 시험 문제가 아니라 작업 절차를 익히기 위한 가상 연습**이다. 실제 시험용 답안을 만들어 반입하는 용도로 사용하지 않는다.

## 한 번뿐인 15분 사전 체험

공식 사실: 링크를 받은 뒤 본 과제 시작 전까지 1회·15분, 동일 작업 환경과 도구·감독 설정을 쓰되 문제는 연습용이다. 체험 작업·예시 답변은 평가되지 않으며 카메라·화면 영상은 녹화 저장하지 않는다고 안내한다. [상세 가이드 p.2]

| 체험 경과 | 확인할 것 | 실전에서 줄이는 위험 |
| --- | --- | --- |
| 0–3분 | 웹캠·전체 화면 공유·Proctor 연결·충전·구도 | 실제 시험 시작 뒤 연결 문제로 시간을 잃는 상황 |
| 3–5분 | README 열기, 작은 파일 작성·저장, `codex`, `/status`, `/model` | 모델과 권한, 입력 위치, 저장 상태를 혼동하는 상황 |
| 5–8분 | 제공 AI로 공개 키트 가져오기·필요한 Skill 읽기. 짧은 명령과 답변 확인 | 개인 파일 업로드에 의존하거나 자동 Skill 등록을 가정하는 상황 |
| 8–11분 | 작은 서버 실행, `0.0.0.0` 바인딩, 실제 포트로 Browser 연결, 수동 클릭 | localhost 바인딩·포트 불일치·서버 탭 종료 |
| 11–13분 | Cofa Helper에 화면·제출 사용법 질문. 필요하다면 MCP 연결 한 번 확인 | 도구 설정에 실전 시간을 쓰는 상황 |
| 13–15분 | 체험 종료와 예시 후속 문항 진입·답변 흐름 확인 | 제출물 확정과 최종 종료를 혼동하는 상황 |

체험에서 MCP가 안 되면 원인을 짧게 확인하고 **직접 터미널 실행 또는 Skill 파일 읽기**로 돌아간다. 기본 작업에 필요 없는 연결을 고치느라 종료 흐름을 놓치지 않는다. 제한을 우회하거나 관리 설정을 바꾸지 않는다. 체험 세션의 파일·설정이 본 과제로 자동 이전된다는 보장은 가이드에 없으므로, 본 과제 시작 때 다시 확인할 준비를 한다.

공개 준비 도구 다운로드는 시험 안의 터미널에서 수행하거나 제공 Codex에 요청한다. 외부 브라우저에서 개인 GitHub를 직접 돌아다니는 절차로 준비하지 않는다. 외부 자료 검색은 제공 AI를 이용하고, 공개 경로와 필요한 파일 이름을 미리 익혀둔다.

## 시험 당일 09:20–10:00

09:20 전후는 이 문서의 준비 제안이며, **09:40 접속과 09:50 추가 안내는 공식 안내**다.

- 09:20: 컴퓨터·휴대폰 전원, 한 대의 모니터, 웹캠, 유선 키보드, 신분증 가림, 물, 조명, 네트워크 점검. 비허용 앱·메신저·외부 AI·원격 접속 프로그램 종료.
- 09:40: 개인 링크 접속. 규정 동의, 웹캠, 전체 화면 공유, Proctor 연결 확인. 설치 QR과 연결 QR을 구분.
- 09:50: 화장실·자리 이탈 관련 추가 메일 확인. 안내된 절차로 확인하고 응시 외 창을 정리. 사전 고정 규칙을 추측하지 않기.
- 10:00: 본 과제를 시작한 뒤 녹화가 시작되면 휴대폰 거치 → Proctor에 신분증 제시 → 안경 확인. 손·키보드·얼굴·모니터 구도 유지.

## 180분 운영표

**경과시간 기준 제안**이다. 공식 타이머가 기준이며 아래 표보다 실제 필수 요구사항과 남은 시간을 우선한다. 10:00에 시작하면 경과 170분은 12:50이다. 이때 제출을 시작해 공식 권고의 10분 여유를 확보한다.

| 경과시간 | 집중할 일 | 남길 결과 |
| --- | --- | --- |
| 0–8분 | 감독 확인 완료, README·기존 지침·파일 구조·실행 방법 읽기 | 요구 결과물, 입력, 필수 파일명, 제공 도구, 모르는 것 |
| 8–20분 | 실무자에게 핵심 모호점 확인, 범위와 완료 기준 결정 | 필수 요구사항 목록과 검증 기준, 중요한 가정 |
| 20–45분 | 가장 중요한 사용자 흐름 하나 구현·실행 | 입력부터 결과까지 이어지는 최소 작동 결과 |
| 45–100분 | 남은 필수 기능을 작은 단위로 추가 | 각 기능의 실행 결과와 확인한 실패 조건 |
| 100–135분 | 통합·경계값·실패 흐름 검증, 실제 사용성 확인 | 재현 가능한 검증, 발견한 오류와 수정 |
| 135–155분 | 주요 결함 수정, 불필요한 기능 축소 | 요구사항별 완료·미완료·확인 못 함 구분 |
| 155–170분 | 실행법·판단 근거·검증·한계 정리, 최종 실행 | 실제 구현과 일치하는 제출 문서와 저장된 파일 |
| 170–180분 | 제출 미리보기·필수 파일·저장 상태 확인 후 확정 | 제출물 고정, 후속 질문 준비로 이동 |

135분 이후에는 새로운 기능보다 필수 기능의 실패를 줄이는 것을 우선한다. 이는 점수 공식이 아니라 마감 전 완결성을 확보하기 위한 전략이다. 시작부터 화면을 꾸미거나 새로운 인프라를 설치하는 것이 요구사항 해결보다 앞서지 않게 한다.

### 첫 20분에 확인할 질문

README에 이미 답이 있으면 다시 묻지 않는다. 실무자 에이전트에는 구현 결과를 바꾸는 질문을 짧게 묶어서 묻는다.

- 누가 어떤 일을 끝내기 위해 사용하는가? 성공을 확인하는 구체적인 행동은 무엇인가?
- 여러 목표 중 반드시 해결해야 하는 것은 무엇인가?
- 입력의 단위·형식·누락값·중복은 어떻게 해석하는가?
- 경계값이 같을 때 처리, 동점 순서, 오류 시 기대 동작은 무엇인가?
- 제출해야 하는 파일·실행 방법·평가할 수 있는 결과물은 무엇인가?

화면 사용법은 Helper, 업무 규칙은 실무자, 장애는 문제 신고로 구분한다. 실무자에게 “전부 어떻게 만들까요?”처럼 설계 전체를 넘기기보다, 선택에 영향을 주는 불확실성을 확인한다.

### Codex에 주는 첫 요청

복사할 시작 요청은 [README 2번](../README.md#2-제공-codex에-시작-요청-보내기)에 있다. 이미 시작했다면 같은 요청을 반복하지 않고 현재 단계에서 계속한다.

이후 요청은 목표·범위·완료 조건·확인 방법으로 좁힌다. 예: “R2의 입력 검증을 구현하고, 빈 값과 경계값이 기대대로 처리되는지 실행해줘. 파일 위치와 검증 결과를 알려줘.” 모델의 답변을 길게 읽기보다 실제 파일과 결과를 확인한다.

### 모델과 도구 운용

공식 권장 목록에서 **Sol 6.1을 시작점으로 쓰는 것**을 제안한다. 이는 이 키트의 운용 선택이며 성능 우위나 점수 가산의 공식 근거는 아니다. 다른 허용 모델이 필요하면 실제 `/model` 목록에서 선택한다. Terra 5.6·Luna 6·Sol 6.0도 안내 목록에 있지만, 자주 교체하면서 맥락을 다시 설명하는 비용을 고려한다. Astra나 외부 모델을 연결하지 않는다.

작업을 분리할 때는 파일 조사·실패 조건 검토처럼 범위가 겹치지 않는 일부터 생각한다. 실제 제공 환경에서 지원·허용되는 기능만 사용한다. 많은 에이전트를 켜는 것이 목적은 아니다. 같은 파일을 동시에 고치거나 결과를 통합하지 못하면 시간을 잃는다.

Skill은 현재 단계에 필요한 것만 읽고, MCP는 과제에 필요한 기능이 있고 짧은 연결 확인까지 끝났을 때 사용한다. 새로운 인증이나 외부 데이터 전송이 필요하면 이 시험의 허용 범위와 맞는지 확인한다. 기본 로컬 작업은 터미널로 계속할 수 있도록 한다.

### 과제 유형별 검증 선택

실제 요구사항이 결정된 뒤 해당하는 행만 사용한다.

| 실제 과제 성격 | 우선 확인할 것 | 보고할 근거 |
| --- | --- | --- |
| 웹 서비스 | 핵심 입력→결과, 빈 상태, 잘못된 입력, 재시작·저장 요구 | 실행 포트, 수동 Browser 확인, 요청/응답 및 관련 테스트 |
| 데이터 분석 | 스키마·단위, 누락·중복, 분모, 표본 편향, 계산 재현 | 데이터 범위, 계산식, 간단한 기준값과 비교, 오류 처리 |
| 규칙·추천·정렬 | 조건 우선순위, 경계값 포함 여부, 동점, 제외 조건 | 작은 수작업 확인 사례와 프로그램 결과 비교 |
| 문서·업무 설계 | 사용자·결정·제약의 일관성, 주장 출처, 실행 가능성 | 요구사항과 문서 위치 연결, 확인된 사실과 가정 구분 |
| AI 기능 포함 | 과제에서 허용한 연결, 실패 시 처리, 근거 없는 출력 방지 | 실제 호출/처리 여부와 검증 한계. 키트가 개인 키나 외부 모델 연결을 허가하지 않음 |

“테스트가 초록색”이라는 말에는 **어떤 기능을 몇 가지 입력으로 확인했는지**를 붙인다. 샘플 하나의 성공을 전체 정확성으로 확대하지 않는다. 과제가 요구하지 않는 유료 서비스나 대규모 모델 학습을 새로 붙이지 않는다.

### 막혔을 때 10분을 지키는 방법

같은 오류에 대한 두 번의 수정으로 진전이 없으면 다음 확인 방법을 바꾼다. 이 횟수는 운영 규정이 아니라 시간 낭비 방지 제안이다.

1. 기대 결과·실제 결과·재현 명령·오류 첫 원인을 짧게 정리한다.
2. 더 작은 입력으로 재현하고 데이터·환경·구현 중 어디에서 실패하는지 나눈다.
3. 필수 요구사항을 유지하는 더 단순한 구현으로 좁힐 수 있는지 판단한다.
4. 플랫폼 오류가 반복되면 시각·단계·오류 문구를 문제 신고로 전달한다.
5. 관리 설정 변경, 모델 변경 우회, 전체 프로세스 종료로 해결하려 하지 않는다.

Browser가 안 열릴 때는 서버 종료 여부 → 실제 포트 → `0.0.0.0` 바인딩 → 경로 순서로 본다. 서버 탭은 유지한다. `3000`에 고집할 이유는 없다. Computer Use 대신 응시자가 수동으로 화면을 확인한다.

## 작업 중 남길 최소 기록

실제 과제가 요구하는 파일명이 우선이다. 과도한 기록을 새로 만드는 대신 요구 문서에 아래 사실이 드러나게 정리한다.

| 기록 | 한 항목에 필요한 내용 |
| --- | --- |
| 요구사항 | 출처, 원하는 동작, 완료 확인 방법 |
| 선택 | 고려한 대안, 선택 이유, 포기한 범위 |
| AI 활용 | 맡긴 범위, 확인·수정한 부분, 실제로 유용했던 결과 |
| 검증 | 입력/명령, 기대 결과, 관찰한 결과, 실패 후 수정 |
| 한계 | 미구현, 확인 못 함, 환경 제약, 후속 개선 |

작업 중에는 제공 Codex의 도움으로 정리할 수 있다. 자료를 외부로 보내지 않는다. **후속 질문에 대비한다는 이유로 하지 않은 결정을 만들어 적거나, 성공 로그를 꾸미지 않는다.** 짧은 실제 기록이 설명하기 쉽다.

## 제출 뒤 질문 준비와 6×5분 답변

공식 안내는 6문항·각 5분이며 상세 가이드의 5문항 캡처는 예시다. 제출 후 질문 준비는 약 5분 안내가 있지만, 상세 화면은 최대 10분과 재시작 가능성을 설명한다. 자동 재시도가 반복되면 안내를 따르고 문제를 신고한다. **14:00 마감은 계속 적용된다.** 10:00에 시작해도 13:30에 반드시 끝나는 구조가 아니며 남은 시간이 정해진 휴식 시간도 아니다. [브리프 p.1, 상세 가이드 pp.4–5]

제출물 확정 후에는 파일을 고칠 수 없다. 준비가 끝나고 시작을 누르면 첫 문항, 직전 답안을 제출하면 다음 문항의 시간이 바로 흐른다. 이전 문항으로 돌아갈 수 없다. **후속 서술형 중 AI와 복사·붙여넣기를 사용하지 않는다.** 아래 방법은 오늘 미리 연습할 사고 순서다.

### 오늘 연습할 5분 답변 구조

| 시간 | 직접 할 일 |
| --- | --- |
| 0:00–0:40 | 질문이 요구한 판단·근거·결과를 구분. 전제가 실제 구현과 맞는지 확인 |
| 0:40–3:40 | 결론 → 이유 → 실제 구현/검증 사례 → 한계를 본인 말로 작성 |
| 3:40–4:40 | 실제 하지 않은 작업·확인 안 한 수치가 들어갔는지 수정 |
| 4:40–5:00 | 질문에 직접 답했는지 확인하고 제출. 다음 문항 타이머가 즉시 시작됨을 기억 |

실제로 묻힐 질문을 예측할 수는 없다. 오늘 연습할 질문은 다음 여섯 가지 정도면 된다.

1. 어떤 사용자 문제를 해결했고 범위를 왜 그렇게 정했는가?
2. 대안 중 이 구현을 선택한 근거와 버린 장점은 무엇인가?
3. AI에게 무엇을 맡겼고 사람이 어떻게 판단·검증했는가?
4. 가장 중요한 오류를 어떻게 발견하고 수정했는가?
5. 어떤 사례를 실행했고, 검증하지 못한 부분은 무엇인가?
6. 시간이 더 있다면 무엇을 먼저 개선하며 왜 그것이 중요한가?

답변은 외운 홍보 문장보다 구체적인 실제 사례로 만든다. “정확도를 높였다”보다 “어떤 입력에서 어떤 오류가 났고, 무엇을 바꾼 뒤 무엇을 다시 확인했는가”가 설명 가능하다. 질문에 없는 기능을 구현했다고 전제하면, 실제 구현과의 차이를 먼저 밝힌다.

마지막 문항 제출 후 자료 처리와 녹화 업로드가 끝나고 **최종 완료 화면**이 나오는지 확인한다. 제출 ID·시각·파일 수·크기를 확인한 다음 브라우저를 닫는다. 단순히 과제 파일을 확정한 상태는 최종 종료가 아니다. [상세 가이드 p.4]
