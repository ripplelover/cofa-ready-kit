## 어떤 문제를 풀었나

여러 제품과 공정의 검사 기록에서 P1 제품의 EDS 검사 결과를 장비별로 집계하는 CLI를 만들었다. 같은 웨이퍼의 재검사와 검사 수량 0인 행을 일부러 포함했다.

가상 실무자에게 먼저 물은 내용은 다음과 같다.

1. 첫 검사와 마지막 검사 중 어느 것을 집계하는가? 시각과 시도 번호가 충돌하면 무엇이 기준인가?
2. 같은 검사 시도 키가 중복되면 동일 행이어도 오류인가?
3. 제외할 제품이나 이전 검사 행도 유효성을 검사해야 하는가?
4. 검사 수량이 0인 행은 남기고 비율을 `null`로 표시하는가?

연습에서는 **최대 시도 번호를 선택하고 그 시도의 장비에 수량을 귀속**하도록 답을 정했다. 모든 행을 검증한 뒤 제품·공정을 필터링하고, 중복 검사 시도는 오류로 처리했다. 이는 이 연습의 명시적인 업무 규칙일 뿐, 내일 데이터에 적용할 기본값이 아니다.

| 집계 | 검사 수 | 통과 수 | 통과율 |
| --- | ---: | ---: | ---: |
| TOOL-A | 110 | 102 | 92.7272727% |
| TOOL-B | 50 | 45 | 90% |
| 전체 | 160 | 147 | **91.875%** |

원본 7행 중 범위에 맞는 행은 5개, 재검사 선택 후 4개다. 이전 시도 1개와 다른 제품·공정 2개를 구분해 기록했다. 비율은 `통과 수 합계 ÷ 검사 수 합계`다. 이 차이만으로 장비의 우열이나 불량 원인을 확정하지 않았다.

독립 검증은 시도 번호 2와 10의 숫자 비교, 재검사 중 장비 변경, 입력 순서 변경, 제품·공정 변경, 가중 분모, 0·빈 데이터, 제외할 행의 오류, 중복 키, 숫자 형식, 잘못된 CSV, 기존 출력과 원본 보존을 포함했다. 18개 검증 실행은 8.088초였다. 작성·동결 후 구현을 읽지 않은 채 첫 검사를 수행했으며 테스트 파일의 실행 전후 해시도 같았다.

## 발견한 차이와 대응

**1. 이 PC에서는 `python3`가 실패했다.** Git Bash에서 `python3 --version`은 종료코드 49였고 `python --version`은 3.10.7을 반환했다. `python`으로 키트가 정상 동작했다. 내일도 `python3 --version`, 필요하면 `python --version`으로 확인하고 성공한 이름을 사용한다. 실행 파일이 검색된다는 사실만으로 판단하지 않는다.

**2. Sol 응답과 파일 작업 성공은 달랐다.** 별도 세션에서 `gpt-6.1-sol`을 요청해 응답을 받았지만, 모델이 시도한 `Get-Content TASK.md`는 `blocked by policy`로 거절됐다. 모델은 과제를 읽지 못했다고 밝히고 재검사 기준과 분모 질문, 올바른 가중 계산 예를 제시했다. 따라서 이 검사는 파일 읽기·수정·코드 실행까지 성공한 사례가 아니다. 요청한 모델 ID와 응답 기록은 있으나 별도의 서버 모델 신원 증명은 없다. 정책을 변경하거나 우회하지 않았다.

**3. `check`는 실제 검토 후에 통과시켰다.** 구현 테스트가 성공해도 요구사항 상태가 `todo`이고 README가 없을 때는 실패했다. 필수 파일을 완성하고 실제 출력·손계산·실패 사례를 읽은 후에만 상태를 바꿨다. `check` 자체가 정답을 판단해 준 것은 아니다.

## 내일 사용할 순서

상세 입력 위치와 오류 복구는 [매뉴얼](MANUAL.md), 반도체 명령은 [실습 가이드](SEMICONDUCTOR-WALKTHROUGH.md)에 있다. 내일은 다음 순서를 사용한다.

1. **제공된 터미널**에서 현재 폴더와 과제 파일을 확인한다. 공개 키트를 받아 Python 버전 확인 후 스킬을 설치한다. 기존 `.cofa-kit`이 있으면 덮어쓰지 말고 상태를 확인한다.
2. 제공 `codex`를 열고 `/status`, `/model`에서 허용 모델을 확인한다. 개인 로그인·API 키를 가져오지 않는다.
3. **Codex 입력란**에서 `$cofa-triage`와 실제 과제 읽기를 요청한다. 스킬이 보이지 않으면 `.cofa-kit/skills/cofa-triage/SKILL.md`를 읽고 적용하도록 요청한다.
4. 반도체 데이터라면 `$cofa-semiconductor`로 개체 키·검사 단계·분모·재검사 규칙부터 확인한다. 임의로 마지막 행을 택하지 않는다.
5. `$cofa-build`로 핵심 기능 하나를 실행한다. `$cofa-verify`로 손계산, 잘못된 입력, 과제가 요구한 실제 사용 흐름을 검사한다.
6. 실제 명령과 결과를 기록하고 요구사항·필수 파일·한계를 검토한다. 웹 과제라면 본인이 Browser에서 조작한다.
7. **제출 확정 전에만** `$cofa-explain`으로 선택 이유를 설명하는 연습을 한다. 실제 후속 서술형에서는 AI와 붙여넣기를 사용하지 않는다.
8. 제출물 확정뿐 아니라 후속 문항과 업로드까지 끝내고 최종 완료 화면을 확인한다.

**15분 사전 체험에서 남은 확인:** 제공 Codex가 파일을 읽고 수정하고 명령을 실행할 수 있는지, 허용 모델이 응답하는지, 공개 저장소 다운로드와 스킬 호출이 되는지, Browser·제출 화면이 어떻게 동작하는지 확인한다. MCP는 필요할 때만 실제 도구 호출까지 확인하고, 연결에 막히면 같은 기능의 CLI로 진행한다. Proctor·촬영·신분증·화면 공유도 별도로 직접 확인해야 한다. 사전 체험 파일·설정의 본 시험 유지 여부는 아직 확인하지 않았다.

## 오늘 본인이 5분 안에 설명해 볼 내용

- 왜 재검사 선택 기준을 먼저 물었고, 임의 선택은 결과를 어떻게 바꾸는가?

- 0분모, 중복 검사, 장비 변경을 어떻게 처리했고 어떤 실행으로 확인했는가?
- AI에게 맡긴 일과 검토한 증거는 무엇이며, 아직 검증하지 않은 것은 무엇인가?

위 질문은 이 합성 연습용이다. 실제 서술형 질문을 예측하거나 시험 중 답변을 대신 작성하는 자료가 아니다. 연습 구현과 원시 실행 로그는 로컬 비공개 폴더에 보존했고 공개 저장소에는 이 요약을 담았다. 기존 키트 자체 49개 테스트와 이번 합성 과제의 10개·18개 테스트는 서로 다른 검사다.
