# 기존 프로젝트의 오류를 고칠 때

실제 과제가 기존 코드의 동작을 바꾸거나 결함을 수정할 때 읽는다. 특정 언어·주문 API·반도체 주제를 가정하지 않는다. 현재 과제 안내와 기존 프로젝트 지침이 기준이다.

## 1. 바꾸기 전에 동작과 계약을 확인한다

- 실제 프로젝트의 README·설정·의존성 잠금 파일·실행 스크립트·테스트를 읽는다. `package.json`이 있으면 해당 scripts와 패키지 관리자를 확인하고, 존재하지 않는 `npm test`나 Python 테스트를 임의로 정하지 않는다.
- 기존 사용자 변경을 확인하고 유지한다. 실행에 필요한 환경변수는 이름·용도만 확인하며 값을 출력하거나 개인 비밀키를 가져오지 않는다.
- 유지할 계약을 적는다: 함수/API 입력·출력·상태코드, 검증·오류 응답, 식별자 의미, 저장 상태와 부작용. 문제와 무관한 인증·스키마·파일명·정상 동작을 바꾸지 않는다.
- 수정 전에 작은 입력으로 문제를 재현하고 기대값·실제값·명령을 남긴다. 기존 검사를 실행할 수 있으면 현재 결과도 기록한다. 의존성·환경 오류로 실행하지 못한 경우와 실제 기능 실패를 구분한다.

## 2. 결함을 잡는 검사를 만든다

필수 수정에 직접 연결되는 회귀 테스트를 기존 테스트 구조에 추가하거나 기존 검사를 강화한다. 가능하면 수정 전에 실패를 관찰해 결함을 잡는 검사임을 확인한다. 실패 재현을 못 했다면 그 한계를 밝힌다. 사용자 파일을 되돌리거나 기존 테스트를 약화해 실패를 만들거나 없애지 않는다.

요구에 맞는 사례만 선택한다.

| 영향받는 동작 | 확인할 사례 |
| --- | --- |
| 일반 입력 처리 | 정상 입력, 필수값 누락, 잘못된 값, 경계값 |
| 재시도·중복 방지 | 같은 요청 반복, 다른 요청 구분, 같은 키에 다른 내용이 온 경우 |
| 동시 변경 | 두 요청이 겹치는 경우, 저장 단계 실패, 중복된 부작용 |
| 외부 작업·비동기 상태 | 성공 확정, 실패 확정, 응답을 못 받아 결과를 모르는 상태 |
| 데이터 변경 | 기존 행·키·단위 보존, 중복·누락·범위 경계, 변경 전후 합계 |

위 사례가 모두 모든 과제의 필수는 아니다. 계약에 없는 처리 기준은 업무 질문으로 확인한다. 예를 들어 timeout은 외부 작업 실패의 확정 증거가 아닐 수 있다. 재시도·취소·보류 중 무엇을 할지는 실제 요구와 관찰한 상태로 결정한다.

## 3. 원인 하나를 최소 변경으로 고친다

입력부터 부작용까지 실제 호출 흐름을 따라 원인을 설명하고, 관련 없는 재작성·패키지 교체를 피한다. 메모리 안에서만 중복을 막는 방식이 여러 프로세스·재시작·동시 요청에도 충분한지 현재 저장 구조와 요구에 맞춰 판단한다. DB 제약·트랜잭션이 필요한지는 실제 프로젝트에서 확인하며 미리 정답으로 강제하지 않는다.

외부 결제·이메일 등 실제 부작용을 일으키는 서비스로 검증 요청을 보내지 않는다. 제공된 테스트 대역·로컬 서비스·격리된 테스트 데이터를 사용한다. 대역으로 확인한 범위와 실제 DB·외부 통합에서 확인하지 못한 범위를 구분한다. 동시성 요구를 순차 재시도 한 번으로 검증했다고 표시하지 않는다.

## 4. 같은 실패와 기존 정상 동작을 다시 확인한다

1. 같은 재현 입력 또는 회귀 테스트로 수정 후 결과를 확인한다.
2. 관련 기존 테스트와 정상·실패 경로를 실행하고 API 계약·저장 상태·부작용을 확인한다. 저장소가 요구하는 빌드·타입 검사도 변경 영향에 맞게 수행한다.
3. 실패를 기존 실패·이번 변경으로 생긴 실패·환경상 미실행으로 나눈다. 테스트를 삭제하거나 기대값을 실제 잘못된 결과에 맞추지 않는다.
4. 테스트 이름·실행 개수·성공/실패/skip을 실제 출력에서 확인한다. 종료코드 0만으로 테스트가 실행됐다고 판단하지 않는다. 테스트 대역 검증을 실제 외부 통합 성공이라고 쓰지 않는다.
5. 검증 후 영향받는 코드·입력·설정을 바꾸거나 병렬 작업을 통합했다면 관련 검사를 다시 실행한다. 예전 성공 로그를 현재 파일의 검증으로 재사용하지 않는다.

## 5. 실제 요구 문서에 짧게 남긴다

`문제의 재현 → 원인 → 유지한 계약 → 변경과 이유 → 실제 검증 → 남은 한계`를 연결한다. 예시 화면의 `DECISIONS.md`를 필수 제출명으로 추정하지 않는다. 기존 문서·실제 제출 안내에 맞춘다. 참가자가 어떤 실패를 고쳤고 무엇을 확인했는지 직접 설명할 수 있어야 한다.

이 지침은 공개 Cofa의 [개발 과제 시연](https://www.getcofa.com/brochure-v2/workspace-mock.html)을 계기로 보완한 범용 작업 절차다. 시연은 고정된 화면 예시이며 실행 가능한 기출·내일 문제·검증된 해답이 아니다.
